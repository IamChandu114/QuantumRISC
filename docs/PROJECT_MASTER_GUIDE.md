# QuantumRISC Project Master Guide

This document is the developer-facing source of truth for understanding, maintaining, extending, and presenting the QuantumRISC Engineering Platform.

It explains the repository as it exists now:
- Real SystemVerilog RTL
- Real verification and testbenches
- FastAPI backend
- Live simulation, VCD parsing, and WebSocket streaming
- Professional public website
- QuantumRISC Studio engineering UI

The goal is to make the entire system understandable from the top down and the bottom up.

---

## 1. Project Overview

QuantumRISC is a full engineering platform for a RISC-V CPU project. It combines:
- A working RTL implementation
- Verification testbenches
- A Python backend that compiles and runs simulations
- A live Studio UI that visualizes the CPU state
- A public showcase website that launches the Studio

It exists to demonstrate a complete CPU engineering workflow:
- inspect RTL
- compile it
- simulate it
- generate VCD waveforms
- parse live state
- render registers, memory, pipeline, hazards, forwarding, and performance
- present the result professionally

### Why it exists

This is not a toy dashboard. It is a complete portfolio-grade engineering platform that shows:
- CPU microarchitecture understanding
- RTL verification practice
- backend automation
- frontend data binding
- simulation-driven UI visualization
- integration discipline

### Real-world use cases

QuantumRISC can be used for:
- portfolio demonstrations
- recruiter interviews
- internship and graduate interviews
- teaching CPU pipelines and hazards
- exploring SystemVerilog simulations
- showcasing end-to-end hardware/software integration

### Engineering goals

- Keep the existing RTL as the source of truth
- Keep the uploaded Studio UI as the engineering app
- Keep the uploaded Professional Website as the public landing page
- Eliminate mock data from visible UI surfaces
- Drive the UI from actual simulation output
- Preserve a GitHub-ready repository structure

### Connection overview

- The public website is only a launch surface.
- The Studio is the actual engineering console.
- The backend owns all execution and state management.
- The RTL is compiled and simulated by Icarus Verilog.
- The resulting VCD is parsed into live architecture state.

### How the layers interact

1. User opens the website at `/`
2. User clicks `Launch Studio`
3. Browser navigates to `/studio`

6. Backend compiles RTL with Icarus Verilog
7. Backend runs VVP and generates VCD
8. Backend parses the VCD into timeline/state
9. Backend computes metrics, hazards, forwarding, registers, memory, pipeline
10. Studio renders live CPU state

### Simulation layer

#### `backend/app/sim/discovery.py`

Purpose:
- scan the RTL and verification tree
- extract module names
- identify top modules and testbenches

What it does:
- recursively scans `rtl/**/*.sv`
- recursively scans `verification/**/*.sv`
- detects `module` declarations
- identifies `*_tb` testbenches
- prefers `pipeline_cpu_complete` and `cpu_top`

Outputs:
- discovered RTL files
- verification files
- top candidates
- smoke tops
- default testbench

#### `backend/app/sim/compile_manager.py`

Purpose:
- invoke Icarus Verilog (`iverilog`)
- compile selected top/testbench source set

Inputs:
- source file list
- selected top module
- output `.vvp` path
- session work directory

Outputs:
- success or failure
- compiler stdout/stderr
- executable path

#### `backend/app/sim/run_manager.py`

Purpose:
- run the compiled simulation with `vvp`
- locate the generated VCD

Outputs:
- run result
- stdout/stderr
- discovered VCD path

#### `backend/app/sim/vcd_parser.py`

Purpose:
- parse the VCD into signals and time-based changes

What it tracks:
- signal definitions
- time stamps
- changed signal values
- last sample snapshot

Outputs:
- `signals`
- `timeline`
- `samples`
- `max_time`

### Session layer

#### `backend/app/sessions/manager.py`

This is the core backend orchestrator.

Responsibilities:
- create sessions
- hold compile/run state
- drive compilation and simulation
- parse VCD
- compute snapshots
- manage pause/resume/reset/step
- broadcast WebSocket events

Core internal state:
- `SessionRecord`
- `sessions`
- `subscribers`
- `playback_tasks`

#### Session lifecycle

1. Create session
2. Compile
3. Run
4. Parse VCD
5. Publish state
6. Allow playback controls

### Tracker layer

#### `backend/app/trackers/register_tracker.py`

Purpose:
- convert timeline events into register file snapshots

Output:
- 32 architectural registers with ABI names and hex values

#### `backend/app/trackers/memory_tracker.py`

Purpose:
- derive a memory snapshot from the trace

Output:
- base address
- word list

#### `backend/app/trackers/pipeline_tracker.py`

Purpose:

Typical fields:

Purpose:

Output:

#### `backend/app/analyzers/forwarding_analyzer.py`

Purpose:

#### `backend/app/analyzers/metrics_engine.py`

Purpose:
- compute performance metrics from timeline and hazards

Metrics:
- cycles
- retired
- stalls
- hazards
- IPC
- CPI

### Model layer

#### `backend/app/models/schemas.py`

Purpose:
- define API response models
- keep payloads structured and typed

Important models:
- `DiscoveryResponse`
- `SessionCreateRequest`
- `SessionCreateResponse`
- `CompileResponse`
- `RunResponse`
- `SessionSnapshot`

### Backend execution flow

When the frontend asks for a session:
1. Discovery scans the repo

3. CompileManager builds the simulation
4. RunManager executes it
5. VCDParser loads the waveform file
6. Trackers derive architectural views

## 6. RTL

The RTL is the hardware source of truth.

### CPU top-level modules

#### `rtl/cpu/cpu_top.sv`

Purpose:
- simple CPU top
- provides debug outputs for PC and instruction

Good for:
- smoke testing
- lightweight verification

#### `rtl/cpu/pipeline_cpu_complete.sv`

Purpose:
- more complete CPU top for the production simulation path
- includes the pipeline structure and debug-friendly signals

### Core CPU modules

#### `rtl/cpu/pc.sv`

Program counter register.
- synchronous update
- asynchronous reset
- enable support

#### `rtl/cpu/instruction_memory.sv`

Read-only instruction memory.
- currently initialized with a small sample program
- supports combinational fetch

#### `rtl/cpu/decoder.sv`

Extracts:
- opcode
- rd
- funct3
- rs1
- rs2
- funct7

#### `rtl/cpu/control_unit.sv`

Generates control signals:
- RegWrite
- MemRead
- MemWrite
- MemtoReg
- ALUSrc
- Branch
- Jump
- ALUOp

#### `rtl/cpu/immediate_generator.sv`

Generates immediates for:
- I-type
- S-type
- B-type
- U-type
- J-type

#### `rtl/cpu/register_file.sv`

Purpose:
- 32 general-purpose registers
- two read ports
- one write port
- x0 hardwired to zero

#### `rtl/cpu/alu_control.sv`

Purpose:
- converts `ALUOp + funct3 + funct7` into ALU control signals

#### `rtl/cpu/alu.sv`

Purpose:
- performs arithmetic and logical operations

#### `rtl/cpu/execute_stage.sv`

Purpose:
- executes operations using ALU and operand muxing

#### `rtl/cpu/memory_stage.sv`

Purpose:
- wraps the data memory interface

#### `rtl/cpu/writeback_stage.sv`

Purpose:
- selects memory data or ALU result for register writeback

### Pipeline modules

#### `rtl/pipeline/if_id.sv`

Fetch/decode pipeline register.

#### `rtl/pipeline/id_ex.sv`

Decode/execute pipeline register.

#### `rtl/pipeline/ex_mem.sv`

Execute/memory pipeline register.

#### `rtl/pipeline/mem_wb.sv`

Memory/writeback pipeline register.

#### `rtl/pipeline/hazard_detection_unit.sv`

Detects load-use hazards and asserts stall.

#### `rtl/pipeline/forwarding_unit.sv`

Selects forwarding paths for EX operand resolution.

#### `rtl/pipeline/branch_unit.sv`

Computes next PC for branch and jump control flow.

### Memory module

#### `rtl/memory/data_memory.sv`

Purpose:
- synchronous write
- combinational read
- 256-word data memory

### RTL design summary

The RTL is a clean educational RISC-V CPU implementation with:
- clear module boundaries
- pipeline stage decomposition
- hazard handling
- forwarding support
- debug-oriented signals

## 7. Simulation Pipeline

This is the actual flow used by the backend.

### Compile

When the user starts a session or clicks compile:
1. Discovery identifies the relevant source files
2. CompileManager invokes `iverilog`
3. The selected top module and testbench are compiled
4. The backend records stdout/stderr and return code

### Run

When the user runs simulation:
1. RunManager invokes `vvp`
2. The RTL testbench executes
3. The simulation emits a VCD
4. The backend locates the generated waveform file
5. The VCD is parsed into live architecture data

### Pause

Pause stops playback of the parsed timeline.
It does not kill the already completed simulation.
It changes the session playback state only.

### Resume

Resume starts advancing the parsed timeline again.
The backend updates the cursor and rebroadcasts state.

### Step

Step advances the session by one timeline sample.
This is how the user inspects cycle-by-cycle behavior.

### Reset

Reset moves the playback cursor back to the beginning.
It does not rewrite the RTL or rerun the simulation automatically.

### Internal stages

Each run produces:
- compiled executable
- VCD artifact
- parsed timeline
- register snapshot
- memory snapshot
- pipeline snapshot
- hazard summary
- forwarding summary
- performance metrics

## 10. Live Data Flow

This is the most important part of the system.

### Register value flow

1. RTL writes a register in simulation
2. VCD captures the writeback-related signal change
3. VCDParser loads the timeline
4. RegisterTracker reconstructs register values
5. Session snapshot exposes the register file
6. Studio bridge updates `REG_RESULT`
7. Studio UI renders the live register panel

### Memory flow

1. RTL accesses data or program memory
2. VCD records address/data signals
3. MemoryTracker derives a memory window
4. Snapshot exposes the memory data
5. Studio memory and cache views display it

### Pipeline flow

1. PC and instruction signals are captured
2. PipelineTracker extracts stage-level information
3. Snapshot includes current pipeline fields
4. Studio pipeline, trace, and architecture views render them

### Hazard flow

1. VCD timeline is parsed
2. HazardAnalyzer identifies RAW dependencies
3. ForwardingAnalyzer derives bypass paths
4. Session snapshot exposes hazard and forwarding lists
5. Studio hazard and forwarding tabs render them

### Waveform flow

1. Simulation generates VCD
2. Backend stores the VCD in the session run directory
3. VCDParser builds the timeline
4. Snapshot exposes waveform metadata and samples
5. Studio waveform viewer renders the latest trace

### Performance flow

1. Timeline is parsed
2. MetricsEngine counts cycles, retired instructions, hazards, and stalls
3. IPC and CPI are computed
4. Studio performance dashboard shows the result
